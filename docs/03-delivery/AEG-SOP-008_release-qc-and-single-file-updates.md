# AEG-SOP-008 — Release QC and single-file updates

Revision: 0.1 | Status: WORKING_BASELINE | Date: 2026-10-18 | Owner: Dsol (release), SOL/SNET (owned implementation)

Owner requested a clean GitHub-to-GCP release pipeline with OAG-style quality and hash metadata. This procedure applies to every source change, including one-file fixes. It does not replace AEG-SOP-002 cost gates or authorize publication, IAM changes, provider use or deployment.

## Quality basis and limits

This is a project-defined, ISO-aligned QC process. It is not ISO certification or a clause-by-clause conformity assessment. Full licensed standards, organizational controls and independent assessment have not been reviewed here. References were checked against official publisher pages on 2026-10-18.

| Reference | Applied QC theme | Required evidence | Current scope limit |

| [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html) | Software lifecycle processes | Change purpose, requirements, review, configuration identity, verification, release and rollback records | OAG is a read-only process reference; Aegis has its own product boundary |

## One release gate

1. Implement changes in the owning source repository. Identify the requirement/defect, owner, expected behavior, tests and rollback implications. Never copy secrets or runtime databases into Git.
2. For the first upload, run `node tools/prepare-github-first-push.mjs`. It creates an isolated source-only repository at `data/github-first-push` and an exact included/excluded review list next to it. It preserves the original branch, index and history. It does not commit or push. `--refresh` refuses to overwrite independently modified prepared files. Review dependency fixtures as well as source; excluding a test dependency is not a clean release.
3. Open the isolated repository for the first push. Commit only the reviewed staged snapshot to `main`. After the first release, use branches and pull requests in the authoritative GitHub checkout instead of repeatedly exporting snapshots. Do not develop in two independent authoritative repositories.
4. Run `node tools/release-engine.mjs precheck --production` from the prepared/authoritative checkout. Install dependencies with the lockfile and browser dependencies first. All checks must pass: backend types, UI types, release-gate tamper tests, application tests, UI build, documentation verification, secret scan, high/critical dependency audit (including build/test tools) and browser tests. A failed or missing check blocks sealing. Network-dependent audit failure is a failure, not a pass. These checks do not invoke paid models or Google refresh runs.
5. The engine emits a timestamped `data/release-qc/.../qc.json`, including the complete source inventory and log hashes. It detects source changes during checks. A local diagnostic run without `--production` skips browsers and cannot be sealed.
6. From a clean committed checkout, run `node tools/release-engine.mjs seal --receipt data/release-qc/<run>/qc.json`. The engine rechecks all source bytes, commit, required checks and evidence hashes. It refuses an incomplete, failed, changed or uncommitted release. Output is `release.hash.meta.json` plus its SHA-256 receipt in that run directory. Existing receipts are never overwritten.
7. Run `node tools/release-engine.mjs verify --metadata data/release-qc/<run>/release.hash.meta.json` before consuming the source. Store CI evidence with the exact commit. Protect the GitHub default branch with required QC checks and review; workflow files, policy, deploy configuration and the lockfile require review too. A local script can be bypassed: enforcement must also live in GitHub branch/environment rules and GCP IAM.
8. Build one immutable container from that verified commit after the applicable build cost gate. Record commit, source path-bound root, build inputs (including public Maps configuration identity without its value), build execution and container digest. Create trusted build provenance/attestation where available. A source seal alone does not cover a Docker image or runtime configuration.
9. After owner approval and the deployment cost gate, Dsol deploys that exact image digest to the production Cloud Run service. Preserve Secret Manager references, explicit role permissions, noindex, budgets and service limits. Record actual revision URL, effective configuration, health/smoke results and the prior image digest/revision for rollback. Production model access stays Flash default for all; Flash-Lite/Argon Pro OR Admin only, enforced on the server.
10. Reconcile billing per SOP-002. SQLite ephemeral-storage loss on a redeploy is a known unresolved limitation; decide persistence/backup before any production state is treated as durable. No production-ready claim until this is addressed for the intended operational scope.

## Single-file update

Create a small branch and PR changing the intended source file plus necessary tests/documentation. Run the same full gate, optionally annotate it with `--changed ui/src/example.tsx`. This annotation does not narrow checks or authorize other changes. The complete source inventory and commit are sealed again. Build a new image and deploy its digest; never hot-copy a source file into a running Cloud Run revision. Retain the previous approved digest for rollback. Any edit after QC requires a new QC run and seal; do not change an old seal or backdate evidence.

## Roles and release disposition

SOL/SNET fix owned code and tests. Dsol assembles evidence and executes only authorized, gated release actions. Owner approves release, access and spending decisions. Review must be independent where feasible; if independent review is absent, record it as pending, not approved.

Use PASS, FAIL, NOT_RUN and BLOCKED honestly. Hash matches are integrity evidence only. Failures, dependency vulnerabilities, missing source fixtures, documentation drift and unauthorized deployment paths are corrective actions with named owners. Pending manual risk review, signatures, build provenance, approvals, cost gates, hosted smoke and rollback validation stay separate from automated QC.

The local engine is implemented tooling. GitHub protection/environment configuration, production IAM enforcement and actual GCP deployment are separate pending integration work, not made effective merely by adding this SOP.
